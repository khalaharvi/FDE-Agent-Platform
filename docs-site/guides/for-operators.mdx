description: "Take an interview from a recorded conversation to a published, exportable playbook without leaving the review console."

This is the working loop for the person who runs engagements rather than the
one who runs the database: you talk to subject-matter experts, you get what
they said into the graph, you let an agent draft from it, you approve what is
right, and you hand the result to the people who have to follow it.

Everything below happens in the review console or in Claude. There are no
terminal commands on this page. If you would rather see the same loop as SQL
and HTTP — including the privilege denial you can reproduce yourself — read
[Your first merge](/first-merge) instead; it is the same platform from the
other side.

<Note>
The console is the product. The agents draft, but nothing they draft reaches
the graph until a human with the right authority approves it — that is
enforced by database privileges, not by the interface you are about to use.
See [Human gates](/concepts/human-gates).
</Note>

<Note>
Two things have to be true before any of this works, and neither is something
you do yourself. Someone has to be running the console and give you its URL —
that is the [quickstart](/quickstart) locally, or a deployment. And your
sign-in has to hold the **admin** authority, because only an admin can open
the reviewer roster. The first admin on a new database is granted once,
directly against the database, by whoever set the platform up; the prod-ops
runbook (`docs/10-prodops-runbook.md`) carries the statements. On the demo
database that admin is `owner@example.com` — ask to be signed in as them, or
the roster page will refuse you by name.
</Note>

## Before the first interview: who can approve

A proposal cannot clear a gate unless somebody holds the authority for that
gate kind. On a fresh database nobody does, so the first stop is
**`/ui/reviewers`** — the reviewer roster.

Add the people who will review, and grant each the gate kinds they are
qualified for. A reviewer with no authority can open a proposal and read it,
and cannot decide it. The roster is deliberately narrow: the console is the
only thing that can write it, it cannot delete a reviewer or rename a
principal, and CI asserts twelve separate denials to keep it that way. A
reviewer who leaves gets deactivated, not erased, because the decisions they
made still reference them.

## The loop

<Steps>

<Step title="Get the interview in, and check it is actually searchable">
Open **`/ui/sources/new`** and paste the transcript. Give it a title, say
what kind of source it is, and say when it was captured — that timestamp is
what later lets anyone ask what the graph believed at the time.

The form also asks which engagement the transcript belongs to. No console
page creates an engagement, so that id comes from whoever set the platform up;
the field offers the ones that already exist, and on the demo database there
is one waiting for you.

Before anything is stored, the console shows you a preview: how the text was
split into passages, and **how many of those passages anchored to something
the graph already knows about**. Read that number. It is the one thing on
this page that quietly decides whether the rest of the work is wasted.

A passage that anchors to nothing is stored and never retrieved — hybrid
search drops passages with no anchors, so an unanchored transcript is
evidence that exists and cannot be found. The preview tells you the
percentage before you commit, and the source page tells you again after.

<Warning>
Low coverage on the first interview of a new engagement is normal — the graph
has nothing to anchor to yet. Low coverage on the fifth is a signal: the
transcript is discussing things nobody has proposed as nodes, and searching
for them later will return nothing.
</Warning>
</Step>

<Step title="Let an agent draft from what it can now find">
Open **`/ui/agents/run`**. Pick the agent and the task. The dropdown offers
exactly the tasks those two agents perform — the console keeps its own copy
of that list and a test fails the build when it drifts from the agents' — and
each task's form asks for the keys that task actually reads, so there is no
JSON to compose and no field to guess.

The Engagement Agent turns transcript evidence into structured claims. The
Workflow Agent reads the graph at a pinned commit and drafts a workflow from
it. Neither writes anything: both produce a proposal, and the proposal goes
to the queue.

<Warning>
This is the one step that needs AWS. The console dispatches to a deployed
Bedrock AgentCore runtime, and that path is written against verified API
shapes but has not been run against live AWS — see
[Status and honesty](/status). Where no runtime is configured the console
says so and names the terminal command that does the same job, which is a
task for whoever set the platform up. Every other step on this page runs
against a local database with no AWS account.
</Warning>

<Info>
A launch can outlast the browser request that started it — a long transcript
can take minutes, and the front door gives up first. When that happens the
page shows you an error while the agent carries on working.

The console records every launch **before** it dispatches, so that case is
readable rather than silent. **`/ui/runs`** has an **Agent launches**
section: your launch is there either way, with who started it and how it
ended. A record still marked *running* means exactly what it says — nothing
has reported back, so either the agent is still working or the request that
was waiting for it is gone. Check there before launching the same task
again.

What the agent *proposes* still shows up in the review queue rather than on
the page you launched from, which is why a successful launch sends you to
the queue.
</Info>
</Step>

<Step title="Review and merge">
The queue at **`/ui`** is the list of proposals waiting on a person. Open
one and you get the claims the agent is proposing, each with the passages it
is claiming them from — the actual sentences somebody said, not a summary of
them.

Three things you can do with a claim: accept it, edit it, or reject the
proposal. Editing matters more than it looks — a reviewer's edit is kept as
training data with a different label than a clean approval, so correcting an
agent teaches it, and the record of what you changed survives the merge.

When every gate the proposal needs has cleared, **Merge** writes it into the
graph under a new sealed commit. That is the only way anything reaches the
graph, from any surface, ever.
</Step>

<Step title="Publish the workflow">
A drafted workflow is not a runnable one. Open it under
**`/ui/workflows`** and publish it.

Publishing checks faithfulness first: every step that claims to be grounded
in the graph must still point at something that is really there at the
commit the workflow is pinned to. A workflow that drifted from its evidence
refuses to publish rather than publishing a lie.
</Step>

<Step title="Export the playbook">
The workflow detail page has an **Export this playbook as Markdown** link.
It gives you the same document the page shows — the steps in order, what
each one does, who does it, the decision branches, and the graph elements
each step cites, resolved to their labels.

It is plain Markdown with no platform-specific syntax, which is the point:
drop it in an Obsidian vault, a wiki, or a repository and it reads as a
document rather than an export. The people who have to follow the process
never need an account on this platform.
</Step>

</Steps>

## The same loop from Claude

If you work in Claude Code or Claude Desktop, the `fde-operator` plugin puts
the first half of this loop where you already are. It ships three commands —
`/ingest-interview`, `/run-agent`, and `/playbook` — and a skill that
encodes the anchoring discipline described above, so an ingest done through
Claude checks its own coverage instead of silently producing evidence
retrieval will never surface.

The plugin connects as the agent role. It can search, register evidence, and
propose; it structurally cannot approve, merge, or publish, so those stay in
the console under your own identity. That is a property of the database
grants rather than of the plugin's instructions.

Setup and the exact settings are in the plugin's
[README](https://github.com/khalaharvi/FDE-Agent-Platform/blob/main/claude-plugin/fde-operator/README.md).

<Warning>
The install flow is written against Claude Code's documented plugin
behaviour and the on-disk layout of installed plugins; a live
`/plugin install` into a real Claude Code installation has not been
exercised. The MCP server launch it depends on has been.
</Warning>

## When the process changes underneath you

Published workflows are pinned to the graph commit they were drafted from.
When a later merge moves the graph past that pin, the platform raises a
stale-pin signal — for every published workflow behind the new head, whether
or not the merge touched anything that workflow cites. **`/ui/drift`** is
that queue, and the signal records how far behind the pin now is.

So a stale-pin signal is a prompt to look, not a verdict that the workflow is
wrong. Triage is where a human decides whether it matters; when it does, the
correction goes back through the same loop you just ran — an agent drafts it,
a human approves it.

That is the whole point of the pinning. A playbook you exported six months
ago is either still true or has a signal attached asking whether it still is.

## Next step

Open the queue at **`/ui`** and open the top proposal. On a demo database
three are waiting — one nobody has touched, one part-reviewed, and one a
compliance reviewer sent back — and reading a real gate table is the fastest
way to see what you are actually being asked to decide.
